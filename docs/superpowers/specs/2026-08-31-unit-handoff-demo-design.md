# Unit-Granularity Relocatable Handoff Demo Design

**Status:** Approved for implementation on 2026-08-31

**Date:** 2026-08-31

**Extends:** `2026-08-27-relocatable-world-demo-design.md`

## 1. Purpose

Add a second self-contained TypeLayout demo that transfers one game-server unit
at a time. Each unit owns one independent contiguous region. A producer sends an
envelope plus the unit's raw region bytes, and a declared consumer can place the
bytes at a different address, validate them, and use the stored object graph
without per-field decoding or pointer fixups.

The practical scenario is a game-server shard handoff. A source shard migrates
one unit while the destination shard already contains some related units and
does not yet contain others. Links inside the transferred unit use region-relative
pointers. Links to other units use stable IDs and are resolved through the
destination's local registry.

The demo extends, rather than replaces, the existing whole-world checkpoint
demo. Together they show two useful allocation boundaries:

1. one buffer for a complete connected world, useful for checkpoint and whole
   world takeover;
2. one buffer per unit, useful for independently moving, placing, replacing,
   and updating units.

The authoritative evidence must come from actual cross-platform producer and
consumer artifacts. Six platforms each generate a unit artifact, and each
consumer loads the artifacts generated by the other five platforms.

## 2. Exact Claim and Terminology

In this design, "without serialization" means:

- the producer does not encode the unit one field at a time;
- the consumer does not decode or reconstruct strings, vectors, maps, or the
  internal object graph one field at a time;
- the consumer does not traverse the graph to repair pointers;
- transport still copies an envelope and a contiguous byte payload;
- the consumer still performs TypeLayout gating plus strict validation of the
  actual untrusted bytes before any application dereference.

This is direct native-representation transfer for one declared contract. It is
not zero-copy networking, and it is not compatibility with arbitrary builds.

"Unit" is the independently transferable ownership boundary. Every owning
allocation reachable through its stored containers and internal pointers is in
the same unit region. A stable `UnitId` is not a pointer and may name a unit in
another region.

## 3. Success Criteria

The local demo must show:

- one source unit in one independently owned region;
- an envelope containing the source unit's raw region bytes;
- source and destination regions alive simultaneously at different addresses;
- unchanged raw region offsets after the copy;
- dynamic strings, vectors, and a frozen flat map;
- a vector whose elements are relative pointers;
- null, shared, and cyclic internal pointer relationships;
- successful destination registration under the transferred `UnitId`;
- one external ID that resolves to another independently owned destination
  unit and one external ID that remains unresolved without rejecting handoff;
- normal post-handoff mutation of the transferred unit;
- the required Admission, Agreement, foreign-handle, and corrupted-offset
  negative cases.

The native evidence matrix must additionally show, for the unit contract:

- 24/24 platform Admission decisions;
- 60/60 named Agreement decisions: four contract types across 15 unordered
  platform pairs;
- 30/30 directed transfers: six consumers loading five foreign producer
  artifacts each;
- complete source, toolchain, artifact, and execution provenance.

The world and unit results remain independently countable. A passing combined
run may also summarize 120/120 named Agreement decisions and 60/60 directed
transfers, but those aggregate counts must not obscure which scenario passed.

## 4. Scope and Non-Goals

### 4.1 In Scope

- One `UnitSnapshot` root per region.
- Existing `relative_ptr`, `region_string`, `region_vector`, and
  `region_flat_map` representations.
- Internal relative links that never leave their unit region.
- Stable integer IDs for cross-unit relationships.
- A small destination registry that owns independent validated unit buffers.
- A unit-specific checkpoint schema and object-graph validator.
- The existing whole-region relocation Admission profile.
- Four explicit unit Agreement keys.
- One local executable, focused C++ tests, evidence-pipeline tests, and the
  authoritative six-platform run.
- The smallest internal refactor needed to share region construction and
  envelope loading with the world demo.

### 4.2 Explicit Non-Goals

- Real sockets, RPC, retry, authentication, or transport security.
- Incremental, delta, or compressed transfer.
- Concurrent handoff, transactional rollback, or distributed ownership
  consensus.
- A `relative_ptr` that crosses region or unit boundaries.
- Automatically migrating units referenced by the transferred unit.
- A global shared arena for multiple unit buffers.
- Schema evolution or semantic conversion.
- Cross-endian, 32-bit, or non-declared platform compatibility.
- A general serialization, object database, allocator, or validator framework.
- Inventory, equipment, skill-tree, AI, or other unrelated game systems.
- Any PowerPoint change; the deck will be updated later from implemented code
  and retained evidence.

## 5. Business Scenario

The source shard owns the canonical migrating unit:

- `id == 1001`;
- `owner_id == 9001`;
- `target_id == 2001`;
- `name == "Ranger"`;
- `hp == 300` before handoff;
- two sorted attributes;
- two effects with dynamic labels;
- an internal cycle between the effects.

The destination shard already owns an independent unit buffer for ID 9001. It
does not own ID 2001. After handoff:

- unit 1001 is registered from the newly loaded buffer;
- lookup of `owner_id` returns the root stored in the separate ID-9001 buffer;
- lookup of `target_id` returns no unit and preserves the unresolved ID;
- unit 1001 remains usable and its HP changes from 300 to 250 without
  reconstructing its containers or graph.

An absent external unit is not malformed region data. Cross-unit resolution is
a registry concern after the transferred buffer is fully validated.

## 6. Stored Data Model

The unit demo owns its domain names and does not depend on the world schema:

```cpp
namespace relocatable_unit_handoff_demo {

using UnitId = std::uint64_t;

struct UnitPosition {
    std::int32_t x;
    std::int32_t y;
};

enum class EffectKind : std::uint8_t {
    shield,
    haste
};

struct Effect;
using EffectRelativePtr = relative_ptr<Effect>;

struct Effect {
    std::uint32_t id;
    EffectKind kind;
    std::int32_t magnitude;
    region_string label;
    EffectRelativePtr next;
};

using AttributeEntry =
    region_key_value<std::uint32_t, std::int32_t>;

struct UnitSnapshot {
    UnitId id;
    UnitId owner_id;
    UnitId target_id;
    UnitPosition position;
    std::int32_t hp;
    region_string name;
    region_vector<Effect> effects;
    region_flat_map<std::uint32_t, std::int32_t> attributes;
    region_vector<EffectRelativePtr> effect_order;
    EffectRelativePtr selected_effect;
};

} // namespace relocatable_unit_handoff_demo
```

The canonical internal graph is:

- `effects` contains exactly two elements, A and B;
- `A.next` points to B and `B.next` points to A;
- `selected_effect` points to A;
- `effect_order` contains A, B, A, and null;
- the repeated A pointer demonstrates sharing;
- the final entry demonstrates nullability.

The two effects and their labels are sufficient to demonstrate a dynamic array
of records, nested dynamic strings, a recursive relationship, sharing, an
internal cycle, and a dynamic container of movable pointers.

## 7. TypeLayout Contract

The unit contract has exactly four named types:

1. `UnitSnapshot`;
2. `Effect`;
3. `EffectRelativePtr`;
4. `AttributeEntry`.

All four are evaluated under
`TransferProfile::whole_region_relocation`. The same closed
`region_relocation_traits` approach used by the world demo admits the unit root
and effect record only when each stored member representation is admitted.

`EffectRelativePtr` has a finite, non-opaque signature. Its signature describes
the pointer representation and pointee type identity but does not recursively
expand the complete `Effect` object graph. Runtime recursion and type-layout
signature construction are separate concerns; the `A -> B -> A` cycle does not
require an opaque contract token.

The contract deliberately lists `Effect` and `AttributeEntry` separately. The
layout of a frozen vector or map descriptor alone is insufficient to establish
Agreement for its dynamically stored element records.

## 8. Shared Support Boundary

The implementation extracts only the capabilities currently hard-coded to the
world root:

```text
example/
|-- relocatable_region_support/
|   |-- region.hpp
|   |-- region_storage.hpp
|   `-- checkpoint_envelope.*
|-- relocatable_world_demo/
|   |-- world.*
|   |-- world_runtime.*
|   `-- world_checkpoint.*
`-- relocatable_unit_handoff_demo/
    |-- unit.*
    |-- unit_runtime.*
    |-- unit_checkpoint.*
    `-- demo.cpp
```

The physical extraction must not rename the existing region representation
types or change their owning C++ namespace as part of this feature. Type names
are contract inputs, so an aesthetic namespace cleanup could create an
unrelated World signature change. Forwarding headers may preserve old include
paths. A future namespace cleanup is a separate contract change.

The shared support provides:

- fixed aligned region storage;
- construction handles and provenance;
- checked allocation, scalar assignment, descriptor binding, and string
  assignment;
- `RegionBuilder::finish<Root>(region_handle<Root>)` for any valid stored root;
- byte envelope encode/decode and payload copy;
- an internal validation-access capability that exposes bytes, used size, root
  offset, and state transition without exposing unvalidated typed views.

It does not provide:

- automatic schema discovery;
- reflection-driven construction or validation;
- a generic graph walker;
- a public arbitrary `root<T>()` cast;
- cross-region pointer binding.

World and unit code each retain an explicit domain validator and domain-bound
root accessor.

## 9. Construction and Buffer Ownership

`RegionBuilder::finish` becomes a root-type template while retaining all
existing handle checks. A root handle must be non-null and must carry the
current builder address and generation. The change does not weaken the existing
foreign-handle rules.

Every non-null source passed to a `relative_ptr` bind must belong to the same
active builder generation as the destination. Consequently, an effect handle
from unit buffer A cannot be bound into unit buffer B. Cross-unit relations are
stored only as `UnitId` scalar values.

`RegionBuffer` remains move-only. A destination `UnitRegistry` owns buffers by
stable ID. An entry exposes a typed unit root only through the unit-domain root
accessor after the buffer has reached validated state. Moving the owning
`RegionBuffer` object does not copy or rebuild its contained region.

The transferred source and loaded destination remain alive simultaneously
during the local demonstration. This makes the distinct allocation bases
observable and prevents allocator reuse from weakening the relocation proof.

## 10. Checkpoint Envelope and Load Flow

The shared envelope implementation accepts a scenario descriptor instead of
hard-coding the world constants. Existing world wrappers retain their current
magic, format, schema, and behavior. The unit wrapper uses:

- eight-byte magic `TLUNIT\0\0`;
- the existing four-byte `64LE` format tag;
- eight-byte schema `UNITV1\0\0`;
- the existing fixed-width little-endian length, root-offset, flags, and
  checksum fields.

The exact runtime order is:

```text
pre-established Unit TypeLayout Permit
-> decode unit envelope
-> verify format, schema, lengths, flags, root offset, and checksum
-> allocate a fresh aligned RegionBuffer
-> memcpy the complete payload once
-> run UnitRegionValidator
-> mark the buffer validated
-> expose UnitSnapshot through the domain accessor
-> register the buffer under UnitId
-> resolve external IDs through UnitRegistry
```

The loader may be expressed as a small internal generic operation taking an
expected envelope descriptor and a validator callback. Public demo-facing APIs
remain domain-specific, for example `load_unit_checkpoint`. The generic layer
must not let callers select an arbitrary root type for bytes that were admitted
under another schema.

## 11. Unit Validation

Validation is staged so malformed data is rejected before typed access to the
malformed candidate range.

### 11.1 TypeLayout Gate

The build and evidence pipeline establish Admission and Agreement before the
runtime artifact is loaded. If any of the four unit decisions rejects or is
incomplete, the consumer records the result and does not invoke the loader.

### 11.2 Envelope Validation

The unit loader requires:

- exact magic, format, schema, version, and zero reserved flags;
- exact artifact length;
- payload size within region capacity;
- representable root offset;
- valid checksum.

### 11.3 Region Geometry

Before making the buffer visible, `UnitRegionValidator` requires:

- a complete, correctly aligned `UnitSnapshot` root;
- complete and correctly aligned ranges for effects, attribute entries, and
  effect-order pointer elements;
- complete byte ranges for the unit name and both effect labels;
- checked multiplication and addition for every count and offset;
- null descriptor pointers exactly when their corresponding counts are zero;
- pairwise non-overlap for owning ranges;
- strictly increasing, unique attribute keys.

The validator follows the existing world validator's byte-first staging model:
it proves a candidate range before accessing it through its proposed typed
representation.

### 11.4 Internal Object Graph

Every non-null `selected_effect`, `effect_order` entry, and `Effect::next` must
decode to the exact beginning of one element in the validated `effects` range.
A pointer into the middle of an effect is invalid.

The validator checks membership for each stored pointer. It does not recursively
walk `next`, so a valid cycle cannot cause infinite validation. Sharing and
repeated pointers are valid.

Only after all geometry and graph checks succeed may a `RegionView` resolve a
relative pointer or expose a container view.

### 11.5 Registry Resolution

Registry lookup occurs after region validation. `owner_id` and `target_id` are
not treated as offsets and do not participate in region graph validation.
Missing IDs remain unresolved and do not invalidate an independently movable
unit.

## 12. Positive Demonstration

The local executable performs this sequence:

```text
build and validate source unit 1001 in region A
-> capture root and descriptor/link raw offsets
-> encode the unit checkpoint
-> keep region A alive
-> build and register independent owner unit 9001
-> load checkpoint into fresh region B
-> prove base(A) != base(B)
-> prove every captured raw offset is unchanged
-> prove strings, vector, flat map, null, sharing, cycle, and pointer vector
-> register region B as unit 1001
-> resolve owner 9001 from another buffer
-> preserve unresolved target 2001
-> change unit 1001 HP from 300 to 250
-> prove owner unit storage and state are unaffected
```

The sampled offset set includes:

- root offset;
- unit-name data offset;
- effects data offset;
- both effect-label data offsets;
- attribute-entry data offset;
- effect-order data offset;
- selected-effect value;
- both `next` values;
- all effect-order pointer values.

No fixup pass occurs between payload copy and validation.

## 13. Required Negative Cases

There are exactly four unit-specific negative demonstrations:

1. **Native pointer:** an alternative record containing `Effect*` fails
   whole-region Admission. No loader is called.
2. **Packed effect:** a packing-controlled `Effect` remains locally eligible
   but produces a different `Effect` layout signature. Agreement rejects and no
   loader is called. The fixture must prove that the difference is the intended
   contract entry rather than missing evidence.
3. **Foreign handle:** an attempt to bind an effect handle issued by builder A
   into an object owned by builder B throws before either buffer is finalized.
4. **Corrupt internal offset:** a valid unit payload has one `Effect::next`
   value changed to an out-of-range offset, then is wrapped in a newly encoded
   envelope with a valid checksum. Envelope validation succeeds, but graph
   validation rejects before dereference.

The fourth case intentionally recomputes the checksum; otherwise it would prove
only that the envelope detects accidental byte corruption.

## 14. Expected Local Output

The talk-sized output remains equivalent to:

```text
Unit contract: Admission PASS 4/4, Agreement MATCH
Transfer: source base != destination base, raw offsets unchanged
Containers: string=yes vector=yes flat_map=yes
Pointers: nullable=yes shared=yes cycle=yes pointer_vector=yes
Registry: owner 9001 RESOLVED, target 2001 UNRESOLVED
Business: unit 1001 attached, hp 300 -> 250

Negative[native pointer]: Admission FAIL
Negative[packed Effect]: Agreement DIFFER
Negative[foreign handle]: builder REJECT
Negative[corrupt Effect::next]: graph REJECT before dereference
```

The first two contract results summarize build and verification evidence
materialized into the local demonstration. They are not reflection checks
performed on every runtime packet.

## 15. Multi-Scenario Evidence Format

Each of the six native producers generates:

```text
<node>.producer-facts.json
<node>.world.region
<node>.unit.region
```

Producer facts advance to schema 2 and group contracts by scenario:

```json
{
  "schema": 2,
  "node": "x86_64_linux_gcc",
  "contracts": {
    "world": {
      "admission": {},
      "signatures": {}
    },
    "unit_handoff": {
      "admission": {},
      "signatures": {}
    }
  }
}
```

Provenance binds both region files and the facts file by SHA-256 to the same
source commit, workflow attempt, node identity, and locked toolchain. The audit
must reject a missing scenario, a filename escape, a duplicate artifact, a
digest mismatch, a region borrowed from another node, or records mixed across
workflow attempts.

Consumer results retain directed producer and consumer identities and record
separate `world` and `unit_handoff` outcomes. A TypeLayout rejection for one
scenario prevents loading only that scenario; it must not be silently replaced
by the result of the other scenario.

The evidence model should gain a scenario dimension rather than duplicate the
entire producer, consumer, audit, and closure implementation. This is the
minimum generalization required by two payload contracts, not a general plugin
framework.

## 16. Six-Platform Matrix

The authoritative nodes remain:

| Node ID | Native platform | Toolchain |
|---|---|---|
| `x86_64_linux_gcc` | Linux x86-64 | GCC 16.2 P2996 |
| `x86_64_linux_clang` | Linux x86-64 | Bloomberg Clang P2996 |
| `arm64_linux_gcc` | Linux ARM64 | GCC 16.2 P2996 |
| `arm64_linux_clang` | Linux ARM64 | Bloomberg Clang P2996 |
| `arm64_macos_clang` | macOS ARM64 | Bloomberg Clang P2996 |
| `x86_64_macos_clang` | macOS x86-64 | Bloomberg Clang P2996 |

Each node uses its own compiled producer to create `unit.region`. No central
host may generate another node's unit payload. Each independently compiled
consumer evaluates and loads the five foreign unit artifacts.

For the unit scenario, every unordered pair records four named Agreement
decisions, yielding 60 decisions. Every ordered pair of distinct nodes records
one runtime transfer result, yielding 30 results.

A unit directed transfer is `PASS` only after:

- all four unit Admission and Agreement decisions permit;
- the foreign unit artifact and provenance are present and bound;
- envelope, region, and internal graph validation pass;
- the consumer owns a fresh destination allocation, the loaded payload remains
  byte-for-byte equal to the producer payload, and the sampled relative-offset
  values remain canonical;
- the canonical unit business state and pointer relationships match;
- registry resolution produces owner-resolved and target-unresolved results;
- the destination HP mutation succeeds without affecting another unit buffer.

Producer and consumer run in different processes, so comparing their numeric
virtual addresses would be neither generally available nor meaningful. The
local executable supplies the direct `base(A) != base(B)` proof with both
regions alive at once. The matrix supplies the stronger provenance fact that
foreign bytes generated by another native build are loaded unchanged into a
fresh consumer-owned allocation, with no producer address transmitted and no
fixup mutation.

The final closure is `PASS` only when both scenarios have complete evidence and
their separately required counts pass. Missing unit evidence cannot be hidden
by a passing world result.

## 17. Test Design

### 17.1 `test_relocatable_unit`

- compile-time stored-type properties;
- four-type Admission;
- construction and reading of every container;
- null, shared, cycle, and pointer-vector relationships;
- builder ownership and generation checks;
- foreign-handle rejection;
- destination registry ownership;
- owner resolved and target unresolved;
- HP mutation isolated to the migrated buffer.

### 17.2 `test_relocatable_unit_checkpoint`

- envelope round trip;
- simultaneous source and destination buffers;
- different bases and unchanged sampled offsets;
- truncated input, wrong magic/schema/format, non-zero flags, size mismatch,
  and checksum mismatch;
- root and container range, alignment, count-overflow, overlap, and map-order
  rejection;
- malformed effect-pointer membership rejection;
- a recomputed-checksum corrupt-`next` artifact rejected at graph validation.

### 17.3 `test_relocatable_unit_agreement`

- complete normal fixture matches all four keys;
- duplicate, missing, unknown, or null signature entries are incomplete;
- packed `Effect` produces the intended Agreement difference;
- native-pointer alternative fails Admission;
- a TypeLayout rejection invokes the runtime loader zero times.

### 17.4 Existing and Evidence Tests

- all existing TypeLayout and world tests remain green;
- checked-in World signature fixtures remain intentional and unchanged unless
  a separately reviewed contract change is discovered;
- evidence schema 2 rejects malformed or cross-scenario records;
- workflow tests require both region artifacts at every node;
- audit tests detect artifact substitution and digest mismatch;
- closure tests require exact World and Unit counts;
- the final authoritative workflow runs the real six-node matrix.

## 19. Risks and Controls

### 19.1 Accidental World Contract Change

Moving representation declarations to another namespace could change type
identity and signatures. The implementation preserves existing type names and
verifies checked World signatures and the full World test suite.

### 19.2 Root-Type Confusion

A generic builder finalizer or envelope copier could tempt callers to cast one
schema as another. Domain-specific envelope descriptors, loaders, validators,
and root accessors remain mandatory.

### 19.3 Unsafe Validation of Cycles

Following links recursively can loop or dereference unchecked data. Unit graph
validation inspects raw offsets and validates membership without recursive
traversal.

### 19.4 False Cross-Platform Evidence

Six local smoke tests do not prove cross-platform transfer. The authoritative
workflow retains each producer's actual unit bytes and has all five foreign
consumers load them under bound provenance.

### 19.5 Evidence Count Masking

Aggregate totals could hide a missing scenario. Closure verifies exact counts
for World and Unit separately before optionally reporting combined totals.

### 19.6 Over-Generalization

The shared layer is limited to root finalization, byte storage, envelope
handling, and validation access. Schema enumeration, semantic graph checks, and
business operations stay explicit in their domain demos.

3. Every required container and pointer shape is validated and demonstrated.
4. Cross-unit links use only stable IDs; a foreign region handle is rejected.
5. Runtime corruption is rejected before application dereference.

## 21. Claim Boundary

The demonstrated claim is:

> For this declared four-type unit contract, a game-server unit whose owning
> data and internal relative links are contained in one region can be transferred
> as one byte payload among the six locked 64-bit little-endian builds. A
> permitting consumer can validate and attach the unit at a different address
> without per-field deserialization or pointer fixups. Cross-unit relationships
> remain independently transferable because they use stable IDs resolved by the
> destination registry.

The demo does not establish compatibility with undeclared builds, arbitrary
native objects, cross-region pointers, schema evolution, big-endian or 32-bit
systems, or a production network protocol.
