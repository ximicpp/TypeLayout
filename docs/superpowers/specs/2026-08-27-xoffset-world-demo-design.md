# XOffset World Checkpoint Demo Design

**Status:** Written design awaiting review

**Date:** 2026-08-27

**TypeLayout worktree:** `cppcon2026-deck`

**XOffset baseline:** `next_cpp26` at `2233004983cd42664e3d6084ec09092b2968ad4e`

## 1. Purpose

Add one small, practical TypeLayout demo built on XOffsetDatastructure. The demo models a game-server world checkpoint that can be saved, loaded at a different region base address, queried, modified, and saved again without pointer fixups.

The demo must prove two separate conditions before loading application data:

1. **Admission:** every declared representation is suitable for the selected whole-region relocation profile.
2. **Agreement:** every declared representation has the same TypeLayout signature as the producer evidence.

The demo then relies on XOffset's verified wire loader for its container and allocator structure and adds a narrow validator for application-defined relative pointers.

This is the smallest scenario that still has practical meaning and demonstrates why movable pointer representations matter: one `relative_ptr<T>` makes null links, shared targets, cycles, and pointer-containing containers possible inside a relocated region.

## 2. Success Criteria

The implementation is complete when one executable demonstrates all of the following:

- a world with two entities, dynamic strings, a dynamic entity array, an ID index, and a vector of relative pointers;
- null, non-null, shared, cyclic, and container-stored relative links;
- a successful Admission decision for a whole-region relocation profile;
- a successful four-type Agreement check against producer evidence;
- verified save and load with the source region kept alive and different source and destination base addresses;
- unchanged raw relative deltas after relocation and correct graph relationships without fixups;
- a practical query, an in-place state mutation, and a second verified save/load;
- rejection of a native-pointer alternative by Admission;
- rejection of a real packing variant by Agreement;
- rejection of one corrupted relative delta by the graph validator.

No deck file is changed in this phase. Deck-facing observations can be recorded after the working demo exists.

## 3. Scope and Non-Goals

### 3.1 In Scope

- A minimal public TypeLayout Admission extension for address dependence and transfer profile selection.
- Demo-local TypeLayout customizations for the XOffset types actually used.
- A fully reflected, four-byte `relative_ptr<T>` with no opaque signature.
- A finite, explicit list of region-stored types whose signatures form the demo's Agreement contract.
- Checked-in producer signature fixtures generated by the existing `SigExporter` machinery.
- XOffset `save_verified<T>()` and `load_verified<T>()` for wire, allocator, and container validation.
- A demo-specific relative-pointer and ID-index validator.
- Compile-time and runtime regression coverage for the positive and three negative cases.

### 3.2 Explicit Non-Goals

- A generic `RegionContract` or automatic semantic-dependency closure.
- Recursive expansion of a relative pointer's pointee in its layout signature.
- Changes to `TypeEntry`, `SigExporter`, fixture format, `CompatReporter`, or opaque registration.
- A new permit/wrapper/state-machine abstraction around the loader.
- Full hostile-input parsing or replacement of XOffset's structural validator.
- Schema evolution, semantic compatibility, cross-endian conversion, or a universal wire format.
- Independent relocation of an entity array, pointer array, pointer object, or pointee.
- Use of `XCompactor` after links have been established.
- A general claim that arbitrary non-trivially-copyable C++ objects may be relocated with `memcpy`.
- Additional domain features such as items, inventories, attributes, achievements, sets, shards, or parent hierarchies.

## 4. Practical Scenario

The scenario is a trusted, same-system game-server checkpoint used for process takeover. A server builds a compact world region, proves that its declared native representations are admitted and agree with producer evidence, saves the region, and loads it into a second live buffer at another base address. The receiving process can immediately follow in-region relationships, query party health, update the tick and boss health, and checkpoint the updated state.

The two entities are `Hero` and `Boss`:

- The initial checkpoint has `tick == 42`, `Hero.hp == 120`, and `Boss.hp == 300`.
- `Hero.owner` is null.
- `Boss.owner` points to `Hero`.
- `Hero.target` points to `Boss`.
- `Boss.target` points to `Hero`, completing a cycle.
- `local_player`, `Boss.owner`, and `party[0]` share `Hero` as a target.
- `party` contains `[Hero, Boss]`, storing both links as dynamic container elements; its initial total HP is 420.
- `entity_index` maps the two stable IDs to indices 0 and 1 for normal application lookup.

This graph supplies every pointer shape the demo needs without adding a third entity or another container family.

## 5. Data Model

The demo uses fixed-width representation types throughout:

```cpp
struct Position {
    std::int32_t x;
    std::int32_t y;
};

enum class EntityKind : std::uint8_t {
    player,
    boss
};

struct Entity {
    std::uint64_t id;
    EntityKind kind;
    Position position;
    std::int32_t hp;
    XOffsetDatastructure::XString name;
    relative_ptr<Entity> owner;
    relative_ptr<Entity> target;
};

struct WorldSnapshot {
    std::uint64_t tick;
    XOffsetDatastructure::XVector<Entity> entities;
    XOffsetDatastructure::XMap<std::uint64_t, std::uint32_t> entity_index;
    XOffsetDatastructure::XVector<relative_ptr<Entity>> party;
    relative_ptr<Entity> local_player;
};
```

The implementation registers a stable XOffset schema name for `WorldSnapshot`, as required by XOffset's verified wire format.

### 5.1 `relative_ptr<T>` Representation

`relative_ptr<T>` contains exactly one data member:

```cpp
std::int32_t delta_;
```

Its contract is:

- `delta_ == 0` encodes null.
- A non-zero delta is measured from the address of `delta_` to the first byte of the target object.
- The type is standard-layout and trivially copyable.
- `sizeof(relative_ptr<T>) == 4` and `alignof(relative_ptr<T>) == 4` are compile-time requirements.
- `reset(target, region)` accepts null or requires both the pointer object and target to be within the same region, and rejects a difference that cannot be represented by `std::int32_t`.
- `raw_delta()` exposes the integer representation for validation and demonstration.
- `get()` resolves the encoded address and is used only after graph validation.

The TypeLayout signature reflects the real `std::int32_t` member. It does not use `O(...)` and it does not inspect `T`. Consequently, `relative_ptr<Entity>` has a finite representation signature even though runtime `Entity` objects form a cycle. Runtime graph recursion and layout-signature recursion are separate concerns.

## 6. Minimal TypeLayout Admission Extension

The change is confined to `include/boost/typelayout/admission.hpp`. Existing `is_byte_copy_safe<T>` behavior remains available and no existing exporter or reporter API changes.

### 6.1 Public API

```cpp
enum class SourceContext {
    independent,
    same_region,
    address_space_dependent
};

enum class TransferProfile {
    ordinary_copy,
    whole_region_relocation
};

template <typename T>
struct source_context_traits {
    static constexpr SourceContext value =
        detail::default_source_context<T>();
};

template <typename T>
struct region_relocation_traits {
    static constexpr bool enabled =
        std::is_trivially_copyable_v<T>;
};

template <typename T>
inline constexpr SourceContext source_context_v =
    source_context_traits<std::remove_cv_t<T>>::value;

template <typename T, TransferProfile Profile>
inline constexpr bool is_admitted_v =
    detail::is_admitted<std::remove_cv_t<T>, Profile>();
```

`SourceContext` records what original address context a representation depends on:

- `independent`: no original address is encoded;
- `same_region`: relative values remain valid only when their containing region and targets move by one common displacement;
- `address_space_dependent`: a process address, reference, member pointer, or equivalent representation is present.

The primary `source_context_traits<T>` calculation follows actual bases, members, and array elements and joins their contexts. Its recursive steps call the public `source_context_v<Member>` customization point rather than bypassing specializations. Raw pointer-like language types produce `address_space_dependent`. A full specialization replaces this default recursion by supplying one `static constexpr SourceContext value`.

The join is explicit, with `address_space_dependent` dominating `same_region`, which dominates `independent`; the implementation must not rely on the numeric ordering of the enum.

### 6.2 Admission Predicates

The profiles are defined exactly as follows:

```text
ordinary_copy =
    std::is_trivially_copyable_v<T>
    && is_byte_copy_safe_v<T>
    && source_context_v<T> == SourceContext::independent

whole_region_relocation =
    is_byte_copy_safe_v<T>
    && region_relocation_traits<T>::enabled
    && source_context_v<T> != SourceContext::address_space_dependent
```

The primary `region_relocation_traits<T>::enabled` is `std::is_trivially_copyable_v<T>`. A full or partial specialization replaces it by supplying one `static constexpr bool enabled`. Non-trivially-copyable types require an explicit opt-in supplied by the owner of their relocation/lifetime contract.

The profile result is a static type-level admission under stated preconditions. It does not prove that a particular relative target is inside a particular region; the runtime graph validator proves that instance invariant.

### 6.3 Demo Adapter

The demo provides only the specializations it needs. The two vector rows refer only to the two concrete instantiations in the data model; this is not a general XOffset adapter:

| Type | Source context | Region relocation opt-in |
|---|---|---|
| `relative_ptr<T>` | `same_region` | inherited from trivial-copy default |
| `XString` | `same_region` | enabled |
| `XVector<Entity>` | `join(same_region, source_context_v<Entity>)` | requires `Entity` whole-region Admission |
| `XVector<relative_ptr<Entity>>` | `join(same_region, source_context_v<relative_ptr<Entity>>)` | requires `relative_ptr<Entity>` whole-region Admission |
| `XMap<std::uint64_t, std::uint32_t>` | `join(same_region, source_context_v<std::uint64_t>, source_context_v<std::uint32_t>)` | requires its `XKeyValue<std::uint64_t, std::uint32_t>` element's whole-region Admission |
| `Entity` | inferred as `same_region` | requires the whole-region Admission of its non-trivial `XString` and relative-link representations |
| `WorldSnapshot` | inferred as `same_region` | requires the whole-region Admission of its exact container and relative-link members |

The XOffset container customizations combine the same-region dependency of their offset-bearing headers with the Admission properties of their dynamic element types. The element signatures still do not become part of the container's TypeLayout signature, so those representations are covered separately by the explicit Agreement contract in the next section. `relative_ptr<T>` is the recursion boundary: its source context is `same_region`, and neither Admission nor its layout signature expands `T`. This avoids pointee recursion without introducing a generic region-closure framework.

The aggregate opt-ins are conjunctions, not unconditional `true` values. With `P` denoting `TransferProfile::whole_region_relocation`, the demo specializations have these exact dependencies:

```text
region_relocation_traits<Entity>::enabled =
    is_admitted_v<std::uint64_t, P>
    && is_admitted_v<EntityKind, P>
    && is_admitted_v<Position, P>
    && is_admitted_v<std::int32_t, P>
    && is_admitted_v<XString, P>
    && is_admitted_v<relative_ptr<Entity>, P>

region_relocation_traits<WorldSnapshot>::enabled =
    is_admitted_v<std::uint64_t, P>
    && is_admitted_v<XVector<Entity>, P>
    && is_admitted_v<XMap<std::uint64_t, std::uint32_t>, P>
    && is_admitted_v<XVector<relative_ptr<Entity>>, P>
    && is_admitted_v<relative_ptr<Entity>, P>
```

This closes the Admission proof through every concrete container and dynamic element while keeping the public change free of generic cycle-detection machinery.

## 7. Finite Region Agreement Contract

A `WorldSnapshot` TypeLayout signature covers its actual object members, including each XOffset container header, but it does not cover objects stored in the containers' dynamic allocations. Therefore the root signature alone cannot establish Agreement for the region.

The demo declares exactly four identifier-safe Agreement keys. The key is the stable name passed to `SigExporter`; the type column records the representation it names:

| Evidence key | Type |
|---|---|
| `WorldSnapshot` | `WorldSnapshot` |
| `Entity` | `Entity` |
| `EntityRelativePtr` | `relative_ptr<Entity>` |
| `EntityIndexEntry` | `XOffsetDatastructure::XKeyValue<std::uint64_t, std::uint32_t>` |

Why each key is present:

- `WorldSnapshot` covers the root and all embedded container headers.
- `Entity` covers the dynamically stored entity representation, including `Position`, `EntityKind`, the `XString` header, and its embedded relative-pointer members.
- `EntityRelativePtr` explicitly covers the dynamically stored `party` element and its whole-region Admission semantics.
- `EntityIndexEntry` covers the dynamically stored map element.

`Position`, `EntityKind`, and the `XString` header need no separate keys because they are embedded in the `Entity` signature. XOffset's private allocator representation is not presented as TypeLayout evidence; compatibility with it is an external precondition fixed by the pinned `next_cpp26` revision and XOffset wire-format v1.

### 7.1 Producer Evidence

`export_signatures.cpp` uses the existing `SigExporter::add_relocatable<T>()` entry point without changing its output format or using the registration macro that calls `add<T>()`. Before it exports anything, it compile-time asserts that all four declared types pass `whole_region_relocation` Admission. This makes successful producer evidence generation conditional on producer-side Admission without adding fields to `TypeEntry`.

Two checked-in artifacts are generated from that one source file by two targets. A compile definition applies `#pragma pack(push, 1)` to `Entity` only for the packing-controlled target. Each target constructs `SigExporter` with an explicit evidence name and registers the same four identifier-safe keys shown above:

- `SigExporter{"producer_ok"}` writes `producer_ok.sig.hpp` for the normal representation;
- `SigExporter{"producer_packed"}` writes `producer_packed.sig.hpp` for the packing-controlled representation that still passes Admission but produces a different signature.

The demo uses a small local Agreement helper, not `CompatReporter`. For each of the four canonical names it requires a fixture entry and compares that entry's layout string with the current build's `get_layout_signature<T>()`. A missing entry or unequal string fails the gate. The normal fixture must match all four; the packed fixture must differ on `Entity`.

No packed object graph is instantiated or loaded. Its sole purpose is evidence that byte-copy eligibility does not imply representation Agreement.

## 8. Construction and Relocation Invariants

A self-relative pointer remains valid only when its own storage and its target receive the same displacement. XOffset container growth can move one allocation without moving another, so graph construction follows a strict order:

1. Create the XOffset buffer and `WorldSnapshot` root.
2. Reserve final capacity for `entities` and `party`.
3. Create both entities, their strings, the ID index, and all party slots.
4. Reacquire the root and element addresses after allocation work.
5. Link every `relative_ptr` only after all relevant storage exists.
6. Freeze topology: do not grow or reorder `entities` or `party`, and do not run `XCompactor`.

After linking, allowed application changes are in-place scalar updates such as `tick` and `hp`. The demo does not claim that arbitrary container mutation preserves self-relative pointers.

`save_verified<WorldSnapshot>()` may normalize and relocate the live region internally. The demo therefore reacquires the root and validates the graph again after every save before using any address derived from the buffer.

## 9. Validation Layers and Trust Boundary

The demo accepts trusted same-system checkpoints, not arbitrary hostile input. Three distinct checks retain separate responsibilities:

1. **TypeLayout Admission and Agreement** run before the loader is called. A failed gate follows a normal `if` branch and prints that loading was skipped.
2. **XOffset `load_verified<WorldSnapshot>()`** validates the v1 envelope, root type and schema hash, allocator state, container deltas, capacities, owned ranges, and nested XOffset structure.
3. **`validate_world_graph()`** validates semantics that XOffset cannot infer for the application-defined `relative_ptr<Entity>` and verifies the ID index.

No `ValidatedWorld` wrapper or permit class is introduced. The demo's sequential control flow makes the gate and validation order visible.

### 9.1 Relative-Pointer Validation Order

For every `owner`, `target`, `party` element, and `local_player`, the validator reads only the raw integer delta first. It performs the address calculation in an unsigned integer address type and does not form or compare a candidate `Entity*` until the integer checks succeed. For a non-null delta it checks, in order:

1. adding the signed delta to the pointer field address cannot overflow;
2. the resulting address lies inside the loaded region;
3. the address satisfies `alignof(Entity)`;
4. the address equals the first byte of one of the live `entities[i]` elements.

Being merely inside the entity allocation is insufficient. A pointer into the middle of an entity is rejected. Only after every relative pointer passes these checks may application code resolve and dereference links.

The validator also requires unique entity IDs and an `entity_index` entry that maps every entity ID to its exact index. These checks make the lookup structure trustworthy without expanding the demo into a general domain validator.

## 10. Positive Execution Flow

The executable follows one linear path:

```text
build source region A
-> reserve entity and party storage
-> populate Hero, Boss, index, and party
-> link relative pointers
-> validate A
-> require four-type Admission PASS
-> require producer_ok Agreement MATCH
-> save_verified(A)
-> reacquire and validate A
-> keep A alive
-> load_verified bytes into region B
-> require base(A) != base(B)
-> validate B before dereference
-> require selected raw relative deltas unchanged
-> verify null/shared/cyclic relationships
-> query total party HP through relative pointers
-> increment tick from 42 to 43 and reduce Boss HP from 300 to 250 in place
-> save_verified(B)
-> reacquire and validate B
-> load_verified into region C
-> validate C and verify the mutation persisted
```

The demo does not compare every payload byte. Different base addresses, unchanged raw deltas, successful pre-dereference validation, and preserved graph relationships are the direct evidence needed for the relocation claim.

## 11. Required Negative Cases

There are exactly three negative demonstrations:

### 11.1 Native Pointer: Admission Failure

A small alternative entity type replaces a relative link with `Entity*`. It is `address_space_dependent`, is not byte-copy safe, and fails `whole_region_relocation` Admission. The executable reports `Admission FAIL` and does not call an XOffset loader for this case.

### 11.2 Packed Entity: Agreement Failure

The current normal build is compared with `producer_packed.sig.hpp`. Both builds satisfy their local Admission assertion, but `Entity` has a different TypeLayout signature. The executable reports `Agreement DIFFER` and skips loading.

### 11.3 Corrupted Delta: Runtime Graph Failure

Starting from a valid verified checkpoint, the test changes one serialized `relative_ptr<Entity>` delta to an out-of-region value. XOffset's verified loader still accepts the otherwise valid envelope and container graph because the application pointer is a trivially copyable leaf. `validate_world_graph()` then rejects it before any dereference.

One corrupted delta is sufficient; separate overflow, misalignment, and interior-pointer demo cases are not added. The validator still implements all required checks.

## 12. Output Contract

The output should be short enough to use in a talk and explicit enough to identify each proof layer. It must include equivalent lines for:

```text
Admission[whole_region_relocation]: PASS
Agreement[producer_ok, 4 types]: MATCH
Relocation: base changed, raw deltas unchanged
Graph: null + shared + cycle + pointer container PASS
Business: party_hp=<value>, tick=<before>-><after>, boss_hp=<before>-><after>
Reload: mutation persisted

Negative[native pointer]: Admission FAIL, load skipped
Negative[packed Entity]: Agreement DIFFER, load skipped
Negative[corrupt rel32]: graph REJECT before dereference
```

Exact punctuation and numeric values may follow the implemented constants, but the three layers and all three skip/reject outcomes must remain visible.

The existing `vendor/XOffsetDatastructure` submodule remains on `next_cpp26`; its source is not modified. The demo includes its public header directly and does not add the vendor project with `add_subdirectory()`.

The successful demo executable is also registered as a CTest test in that configuration.

## 14. Verification and Acceptance Tests

### 14.1 Core TypeLayout Assertions

`test_core.cpp` adds compile-time checks for:

- independent fixed-width values;
- address-space-dependent raw pointers;
- source-context propagation through a small aggregate;
- ordinary-copy rejection of same-region representations;
- whole-region acceptance only when the relocation trait is enabled;
- continued behavior of existing `is_byte_copy_safe_v<T>` tests.

`world.hpp` additionally requires at compile time that `relative_ptr<Entity>` is standard-layout, trivially copyable, exactly four bytes with four-byte alignment, has a generatable TypeLayout signature, and that the signature contains no opaque `O(...)` token.

### 14.2 Demo Assertions

The demo executable fails with a non-zero exit code unless all of these hold:

- the four declared types pass whole-region Admission;
- the normal producer fixture contains and matches all four entries;
- the packed fixture differs;
- source and loaded bases differ while sampled raw deltas remain equal;
- graph validation succeeds before every positive dereference;
- null, sharing, cycle, and party-container relationships are correct;
- ID lookup and party HP query return the expected entities and value;
- tick and Boss HP mutations survive the second save/load;
- the native pointer alternative is rejected without loading;
- the corrupted delta reaches XOffset verified load but is rejected by graph validation.

The full existing TypeLayout test suite must also pass on the supported compiler. No test requires modifying the XOffset submodule.

## 15. Claim Boundary

The demonstrated claim is deliberately narrow:

> For the explicitly declared four-type contract, a trusted XOffset v1 region produced from the pinned `next_cpp26` baseline may be relocated as one unit when every type passes whole-region Admission, producer and consumer TypeLayout signatures agree, XOffset structural verification succeeds, and every application relative pointer validates inside that region.

TypeLayout does not replace XOffset's wire validation, and XOffset does not establish cross-build TypeLayout Agreement. Neither one proves application semantics or general C++ object relocation. The demo is valuable because the combined contract enables a realistic cyclic object graph while keeping each proof obligation visible and independently rejectable.
